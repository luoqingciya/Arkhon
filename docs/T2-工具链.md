# T2 · Go 交叉编译工具链专项

> 关联：`Arkhon Phase0-任务清单.md` · 状态：**构建侧 ✅ / 运行时 dlopen ❌（musl TLS 阻塞，需改加载模型）**
> 日期：2026-09-09

## 目标

打通 **Go c-shared → OpenHarmony `.so`** 完整工具链，产出可被 NAPI 调用的最小 .so，并验证网络 / 加密依赖可编译。

## 结论（三态分项）

| 分项 | 结论 | 证据 |
| --- | --- | --- |
| 最小 .so 交叉编译 | ✅ 通过 | 产出 `aarch64-linux-ohos` 共享对象，导出 `Hello`/`Add` |
| 网络/加密依赖编译 | ✅ 通过 | `getaddrinfo`/`freeaddrinfo` 链接 OHOS musl libc；net/crypto/tls/http 编入 |
| NAPI 运行时调用（dlopen） | ❌ **musl initial-exec TLS 阻止** | 见下「决定性发现」 |
| NAPI 运行时调用（link/DT_NEEDED） | ❌ 同样失败 | 见下「决定性发现」 |

**总体（三态）**：工具链**构建成立**，但「运行时 dlopen 加载 Go c-shared」在 OHOS musl 下**不可行** → 判定为 **收缩**：引擎 A 需改为**独立进程加载内核**（或走 B1 裁剪库）。此结论是 T2 最重要的硬事实。

## 决定性发现：OHOS musl 拒绝运行时加载 Go c-shared .so

真机（API 26）hilog 实测错误，连续两种加载方式均失败：

```
Error relocating /data/storage/el1/bundle/libs/arm64/libhellogo.so:
  initial-exec TLS resolves to dynamic definition in libhellogo.so
```

- **本质**：Go runtime 的 per-goroutine TLS 采用 `initial-exec`（TLSIE）模型。musl 仅在**进程初始链接集**为其预留静态 TLS；对**运行时（dlopen）加载**的库拒绝处理 `initial-exec` TLS → `dlerror` 报错，dlsym 取不到任何符号（`loaded=0`）。
- 该限制与内核实现无关，**任何 Go c-shared .so 在 OHOS musl 下都无法被 dlopen**。
- **link/DT_NEEDED 也无效**：HarmonyOS 的 NAPI `libentry.so` 本身由模块管理器在运行时 dlopen，其依赖仍属运行时加载；实测导致整个 `default/entry` 模块加载失败、`libentry.so` 导入为 undefined。
- 对照：FLclash 在 **Android（bionic）** 上可 dlopen Go 内核；**OHOS（musl）** 不兼容 → 这是与 ClashBox 路径的本质差异点，需单独验证 ClashBox 在鸿蒙的取巧方式。

### 由此导出的可行路线（下阶段决策输入）

| 路线 | 说明 | 与策划书 §2.1 关系 |
| --- | --- | --- |
| **A‘ 独立进程内核** | arkhon-core 编译为**独立 ELF 可执行进程**（自身 exec → 静态 TLS 正常），App 经 loopback HTTP 通信（同桌面端 external-controller 模型） | 引擎 A 变形；需过 T3 验证子进程可拉起/存活 |
| **B1 裁剪库** | 用非 Go 内核/裁剪库替代自编 Go .so | 收缩档 |
| （不可行）dlopen Go .so | 被 musl TLS 封死 | 排除 |

## 工具链配置（含坑）

### 目标与约束

- 平台：Windows（dev）→ **aarch64-linux-ohos**（真机 API 26）
- OHOS 使用 **musl libc**，必须传 `-D__MUSL__`（NDK clang wrapper 默认带）
- NDK 工具链：`<DevEco>/sdk/default/openharmony/native`（clang + sysroot）

### Go 交叉编译参数

```powershell
set CC="<ndk>\llvm\bin\clang.exe --target=aarch64-linux-ohos -D__MUSL__ --sysroot=<ndk>\sysroot"
set CXX="<ndk>\llvm\bin\clang++.exe --target=aarch64-linux-ohos -D__MUSL__ --sysroot=<ndk>\sysroot"
set GOOS=linux
set GOARCH=arm64
set CGO_ENABLED=1
go build -buildmode=c-shared -o libhellogo.so ./hellogo
```

产物：`aarch64-linux-ohos` ELF64 DYN，`Hello`/`Add` 导出为符号 `T`。

## 产物体积（构建侧）

| 产物 | 体积 | 说明 |
| --- | --- | --- |
| 最小 .so（仅 Hello/Add） | ~2.6 MB | cgo + runtime |
| 含网络/加密 .so | ~7.2 MB | 加入 net/crypto/tls/http |

加载耗时 / 崩溃面：dlopen 在 TLS 处即被拒，未深入加载路径（崩溃面待 A’独立进程路线时评估）。

## 网络 / 加密依赖证据

`llvm-nm -D libhellogo.so` 可见：
- `U getaddrinfo` / `U freeaddrinfo` → 解析器走 OHOS musl **libc**（不是 glibc）
- crt 链接 OK，`sigaddset` 等 musl 符号可解析
- crypto（ed25519/rand）、tls/x509、net/http 全部编译 + 链接通过

## NAPI 调用接入（应用侧，探针态）

1. **Go .so**：`entry/libs/arm64-v8a/libhellogo.so`（**stage 模型必须是模块根级 `libs/`，不是 `src/main/libs`**——后者不会被 hvigor 打包，踩坑已移正）。
2. **NAPI C 模块**：`entry/src/main/cpp/napi_init.cpp` + `CMakeLists.txt`，`dlopen("libhellogo.so")` 并回传 `dlerror`。
3. **ArkTS 调用**：`import goNative from 'libentry.so'`，页面「加载 Go .so (T2)」按钮 + `aboutToAppear` 自触发，日志打印 `loaded/hello/add/probe/err`。
4. HAP 内含 `libs/arm64-v8a/libhellogo.so` + `libentry.so` ↔ 已用 `tar -tf` 复核。

### 踩坑记录

- **CC 路径含空格**：`DevEco Studio` 路径有空格，Go 的 CC 空格切分导致失败。方案：无空格目录联接（junction）`experiments/T2-toolchain/ndk → native`，CC 引用 junction 路径。
- **前置 .so 目录**：`src/main/libs` 不打包，须放模块根 `entry/libs/<abi>`。
- ArkTS 严格类型：NAPI 返回 `any` 触发 `arkts-no-any-unknown`，需 `as Record<string, Object>` + 显式 interface。
- **musl final-exec TLS**：dlopen/link 均不可用（见决定性发现）。

## 真机运行时验证（已完成）

hdc 流程已跑通：`list targets` → `install -r <hap>` → `aa start` → `hilog`（`-x -e`/全量 dump 后本地 grep）。设备 10.3.48.43 (API 26)。探针结果见决定性发现。

## 三步结论

- **构建侧**：✅ 继续（Go c-shared 交叉编译成立）
- **运行侧 dlopen**：❌ musl TLS 阻塞 → **排除 dlopen 路线**
- **对引擎 A 的影响**：需改用**独立进程内核**（A’）或走 B1。下阶段（T3）应优先验证 A’：能否在 OHOS app 内拉起 arkhon-core 独立进程并保活。

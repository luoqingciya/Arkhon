# T2 · Go 交叉编译工具链专项

> 关联：`Arkhon Phase0-任务清单.md` · 状态：**构建侧 ✅ / 运行侧 🔁 已由 ClashBox 证伪「不可行」硬结论，改为「需 musl 兼容 Go 工具链」**
> 日期：2026-09-09 · 更新：2026-09-09（T3 深挖 ClashBox 后）

## 目标

打通 **Go c-shared → OpenHarmony `.so`** 完整工具链，产出可被 NAPI 调用的最小 .so，并验证网络 / 加密依赖可编译。

## 结论（三态分项）

| 分项 | 结论 | 证据 |
| --- | --- | --- |
| 最小 .so 交叉编译 | ✅ 通过 | 产出 `aarch64-linux-ohos` 共享对象，导出 `Hello`/`Add` |
| 网络/加密依赖编译 | ✅ 通过 | `getaddrinfo`/`freeaddrinfo` 链接 OHOS musl libc；net/crypto/tls/http 编入 |
| NAPI 运行时调用（dlopen） | 🟢 **真机通过（Gate-B 关闭）** | 见「决定性发现三」：官方 fork（`GOOS=openharmony`，`TLS_GD`）重编 hellogo → Mate 80 Pro 真机 `hilog` 实测 `T2 loaded=1 hello="hello, arkhon" add=5`，**无 initial-exec 报错** |

**总体（三态）**：工具链**构建成立**；运行时 dlopen 失败是**工具链问题，不是平台硬限制** —— 可被 musl 兼容 Go 工具链解除。**引擎 A（进程内 Go c-shared 内核）在手机上可行**，这正是 ClashBox 的路子。原「独立进程内核 A’」与「B1 裁剪库」不再是必需项。

## 决定性发现一（实测）：股票 Go 的 initial-exec TLS 在 OHOS musl 下 dlopen 失败

真机（API 26）hilog 实测错误：

```
Error relocating /data/storage/el1/bundle/libs/arm64/libhellogo.so:
  initial-exec TLS resolves to dynamic definition in libhellogo.so
```

- **本质**：Go runtime 的 per-goroutine TLS 默认用 `initial-exec`（TLSIE）模型。OHOS musl 对**运行时（dlopen）加载**的库只预留静态 TLS，拒绝处理 `initial-exec` TLS → `dlerror`。
- 用**股票 Go 工具链**编的 c-shared .so 确实无法被 dlopen；`link/DT_NEEDED` 亦无效（NAPI `libentry.so` 本身是运行时 dlopen 的）。
- ⚠️ 但这**不是死路**，仅指「股票 Go 默认TLS模型」的死路（见决定发现二）。

## 决定性发现二（T3 深挖，纠正）：ClashBox 在手机上「进程内」跑 mihomo(Go) 内核，且 TLS 可绕过

### 深挖对象：xfz347/xiaobaigroup ClashBox（master 分支，GPL-3.0 开源）

从源码确认其完整技术路线（并非取巧或改 go 源码，而是正规模块 + 上传专用工具链）：

1. **内核形态**：mihomo 以 **c-shared `.so`** 嵌入，经子模块 `proxy_core/src/flclash/core → xfz347/Clash.Meta`（fork）与 `proxy_core/src/flclash/gvisor-ohos → likuai2010/gvisor-ohos` 集成。
2. **进程模型（关键）**：**不需要子进程**。`entry/src/main/module.json5` 声明 `type: "vpn"` 扩展 `ClashVpnAbility`；其 `onCreate` 从 `want.parameters.requestId` 拿到主进程建立的 **VpnConnection requestId**，`new SocketStubService(context).startService(requestId)` —— mihomo 直接跑在 **VPN 扩展进程内**，用 VpnConnection 的 fd 收发隧道流量。手机无 native/ark 子进程**不是阻碍**，ClashBox 压根不依赖子进程。
3. **TUN 栈**：`gvisor-ohos` 把 gvisor 用户态 TCP/IP 栈编译进内核，在用户态完成协议栈（对接 vpn 虚拟网卡 fd），不过度依赖内核 raw socket。
4. **TLS 绕法（决定foundation）**：社区有三条成熟路线，均指向**定制/musl 兼容 Go 工具链**：
   - **Huawei 官方**：`golang/go#71953 「Go general dynamic TLS」`（arm64 Linux/musl，`go tool compile -tls=GD` 使 c-shared 可无 LD_PRELOAD 加载）；
   - `harmony-contrib/log-adaptor`（Huawei 维护）；
   - 社区手改 Go runtime：CocoProxy 对 Go 1.21.13 runtime 打 **12 处补丁**（TLS 寻址两级间接、clone syscall、cgo 初始化），把 mihomo 式 Go 代理编成 `.so` 在 VPN Extension 内 NAPI 加载跑通（见 cocozq.com 记录）。
5. **保活/自恢复**：主 Ability `backgroundModes=[dataTransfer,location,taskKeeping]` + `KEEP_BACKGROUND_RUNNING` + 模拟画中画/下载/定位等「后台运行」策略；另设 **核心恢复** —— 系统杀进程后自动重启内核。

### 对 Arkhon 的结论

- **命题推翻**：原「OHOS 无子进程 + musl TLS → 手机本地 Go 内核不可运行」的硬结论**不成立**。ClashBox 已用「进程内 c-shared + musl 兼容工具链」在手机上跑通 mihomo。
- **正确路径（引擎 A 直接可行）**：mihomo(arkhon-core) 编为 c-shared `.so`（**musl 兼容工具链**），随 HAP 打包；在 plain **VpnExtensionAbility 进程内**由 NAPI 加载；用 `VpnConnection.requestId` 建隧道 fd 并喂给内核。
- **两条前提**：(a) 拿到能产出 musl 兼容 TLS 的 Go 工具链（三选一：带 `-tls=GD` 的 Go 1.24+/1.25+、`harmony-contrib/log-adaptor`、或自行给 runtime 打补丁）；(b) 把内核的 TUN netstack 换成 gvisor-ohos 用户态栈（或验证 mint 协议直接读 vpn fd）。

### 修正后的路线表

| 路线 | 说明 | 与策划书 §2.1 关系 |
| --- | --- | --- |
| **A 进程内内核** | arkhon-core c-shared .so，NAPI 在 **VpnExtensionAbility 进程内**加载；`VpnConnection.requestId` 提供隧道 fd | **首推（ClashBox 同款）**，手机上可行，无需子进程 |
| A‘ 独立进程内核 | arkhon-core 独立 ELF 进程 + loopback HTTP | 仅平板/2in1/PC 可行（手机无 native child process）；现为**可选项**，不再必需 |
| B1 裁剪库 | 若自定义工具链不可行，退而求其次 | 收缩档；**注意 sing-box/mihomo 也是 Go，仍需 musl 兼容工具链** |

## 工具链配置（含坑）

### 目标与约束

- 平台：Windows（dev）→ **aarch64-linux-ohos**（真机 API 26）
- OHOS 使用 **musl libc**，必须传 `-D__MUSL__`（NDK clang wrapper 默认带）
- NDK 工具链：`<DevEco>/sdk/default/openharmony/native`（clang + sysroot）

### Go 交叉编译参数（当前为股票 Go，跑通构建侧）

```powershell
set CC="<ndk>\llvm\bin\clang.exe --target=aarch64-linux-ohos -D__MUSL__ --sysroot=<ndk>\sysroot"
set CXX="<ndk>\llvm\bin\clang++.exe --target=aarch64-linux-ohos -D__MUSL__ --sysroot=<ndk>\sysroot"
set GOOS=linux
set GOARCH=arm64
set CGO_ENABLED=1
go build -buildmode=c-shared -o libhellogo.so ./hellogo
```

产物：`aarch64-linux-ohos` ELF64 DYN，`Hello`/`Add` 导出为符号 `T`。

### ⚡ T3 Gate-B 决定性发现三：官方 Go fork `GOOS=openharmony` 已内置 general dynamic TLS（`TLS_GD`）

**纠正两点早前结论**：
1. `go tool compile -tls=GD` 的 general dynamic TLS 目前**只是 proposal（go#71953，华为提交），尚未合入上游**（股票 Go 1.27.1 的 `compile` 无 `-tls` 参数）。所以「股票 Go + `-tls=GD`」并不存在现成开关。
2. `harmony-contrib/log-adaptor` 只是**日志/加载元数据**库，**不是** TLS 解法，不能算备选。

**真正的正解（已实测打通）**：**`openharmony-sig/ohos_golang_go`**（gitcode.com，官方 OHOS SIG）`release-branch.go1.24`，带真 **`GOOS=openharmony`** 端口。其 `src/runtime/tls_arm64.h` 内置 **`TLS_GD`**（general dynamic TLS）宏，正是华为那份未合入上游的补丁，在 OHOS 端口里已启用。

**Gate-B 落地（T3）**：
- 脚本 `experiments/T3-toolchain/build-toolchain.ps1`：用 go1.27.1 自举，`make.bat` 编译出 fork 的 Windows 宿主 `bin\go.exe`（go1.24.5）。
- 脚本 `build-hellogo-ohos.ps1`：`GOOS=openharmony GOARCH=arm64 CGO_ENABLED=1` + OHOS NDK clang，`go build -buildmode=c-shared` 产出 `libhellogo-ohos.so`。
- **静态校验（决定性）**：`llvm-readelf -r` 显示 TLS 重定位已由 initial-exec（`R_AARCH64_TLS_TPREL64`）变为 **`R_AARCH64_TLSDESC`（general dynamic **—— musl 可在 dlopen 的库上处理的形式。
- ⚠️ `hellogo/go.mod` 的 `go` 指令需与 fork 一致（改回 `go 1.24`），并 `GOTOOLCHAIN=local`，避免 fork（1.24）试图自动下载并因网络失败。
- 产物已 stage 到 `entry/libs/arm64-v8a/libhellogo.so`。真机复核结果见下节「真机复核（Gate-B 关闭）」。

### 真机复核（Gate-B 关闭，2026-09-09）

HUAWEI Mate 80 Pro（远程 hdc）安装新打包 HAP 后，`hilog` 实测：

```
T2 loaded=1 hello=hello, arkhon add=5 probe=-2 err=ProbeNetCrypto not exported (optional)
```

- `loaded=1`：`dlopen("libhellogo.so", RTLD_NOW)` 成功，**`initial-exec TLS resolves to dynamic definition` 消失** —— TLSDESC 生效。
- `hello="hello, arkhon"`：Go 导出函数经 `dlsym` + C ABI 调用执行成功 → 证明 .so 在 OHOS musl 上真实运行。
- 注：`ProbeNetCrypto` 因 cgo 对 C 返回导出函数的 codegen 冲突已从 hellogo 移除，napi 侧改为可选符号（缺省 `-2`）。网络/加密运行时校验交由 Gate-D 用真实内核完成。

**结论**：T3 引擎 A 的首要障碍（musl TLS）已解除，可进入 Gate-D（真实内核 .so + VPN 隧道喂流）。

## 网络 / 加密依赖证据

`llvm-nm -D libhellogo.so` 可见：
- `U getaddrinfo` / `U freeaddrinfo` → 解析器走 OHOS musl **libc**（不是 glibc）
- crt 链接 OK，`sigaddset` 等 musl 符号可解析
- crypto（ed25519/rand）、tls/x509、net/http 全部编译 + 链接通过

## NAPI 调用接入（应用侧，探针态）

1. **Go .so**：`entry/libs/arm64-v8a/libhellogo.so`（**stage 模型必须是模块根级 `libs/`，不是 `src/main/libs`**——后者不会被 hvigor 打包，踩坑已移正）。
2. **NAPI C 模块**：`entry/src/main/cpp/napi_init.cpp` + `CMakeLists.txt`，`dlopen("libhellogo.so")` 并回传 `dlerror`。
3. **ArkTS 调用**：`import goNative from 'libentry.so'`，页面「加载 Go .so (T2)」按钮 + `aboutToAppear` 自触发，日志打印 `loaded/hello/add/probe/err`。
4. HAP 内含 `libs/arm64-v8a/libhellogo.so` + `libentry.so` ↔ 已用 `tar -tf` 复核。

### 踩坑记录

- **CC 路径含空格**：`DevEco Studio` 路径有空格，Go 的 CC 空格切分导致失败。方案：无空格目录联接（junction）`experiments/T2-toolchain/ndk → native`，CC 引用 junction 路径。
- **前置 .so 目录**：`src/main/libs` 不打包，须放模块根 `entry/libs/<abi>`。
- ArkTS 严格类型：NAPI 返回 `any` 触发 `arkts-no-any-unknown`，需 `as Record<string, Object>` + 显式 interface。
- **musl TLS**：股票 Go 的 initial-exec TLS 导致 dlopen 失败（见决定发现一）；须换 musl 兼容工具链（见「T3 前置」）。

## 真机运行时验证（已完成）

hdc 流程已跑通：`list targets` → `install -r <hap>` → `aa start` → `hilog`（`-x -e`/全量 dump 后本地 grep）。设备 10.3.48.43 (API 26)。探针结果见决定发现一。

## 三步结论

- **构建侧**：✅ 继续（Go c-shared 交叉编译成立）
- **运行侧 dlopen**：🔁 股票 Go 失败，但 **ClashBox 已证伪「平台不可行」** → 改为「需 musl 兼容 Go 工具链」。**改换含 GD TLS 的工具链后重测 Gate-B 加载**。
- **对引擎 A 的影响**：✅ **A（进程内内核 + VpnExtension + gvisor-ohos）回到手机可行主线**，是下阶段 T3 的主攻方向（对齐 ClashBox）。

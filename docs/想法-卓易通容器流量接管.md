# 想法：卓易通容器流量接管（ClashBox「兼容模式」参考）

> 状态：**待讨论**（2026-09-29 记录）——尚未纳入路线，不改变现有接管范围结论。
> 相关：`Arkhon 后续开发计划.md` §2「接管范围边界」排查记录。

## 1. 问题背景

Arkhon 的 VPN 隧道当前只能接管**鸿蒙三方应用**的流量（夸克、观星等可接管）；以下两类不在接管范围（平台限制）：

- 系统应用（如华为浏览器）
- 经「卓易通」兼容层运行的安卓应用（如 Chrome）——兼容层网络栈独立于鸿蒙，流量不走系统 VPN

对照观察：**卓易通内的安卓代理软件可代理「卓易通安卓应用 + 鸿蒙三方应用」**（系统应用同样不可）——兼容层路径的接管面反而更大。若能反过来让 Arkhon 覆盖容器流量，接管面可对齐甚至反超。

## 2. ClashBox「兼容模式」的推测原理

> 说明：ClashBox 未公开源码级实现，以下为基于鸿蒙网络架构与社区反馈的**推测**，仅供讨论参考。

核心目标：让 VPN 隧道同时「看到」鸿蒙原生应用 + 卓易通容器内应用两股流量。

可能的技术路径：

1. **路由规则校准**（推测为核心）：默认模式下 VPN 接口的路由规则可能未把容器内部网段（如 `172.17.x.x`）指向隧道；兼容模式或新增了针对容器网段的特定路由条目。
2. **网络命名空间桥接尝试**：卓易通拥有独立网络命名空间（隔离根源）；兼容模式或在用户态通过 IPC / 转发机制桥接两个命名空间——例如容器侧部署轻量转发组件，把流量经特定通道送往主系统的代理进程（类似「跨系统代理调试方法」专利思路）。
3. **VPN 接口差异化配置**：或调整 TUN 创建时的网络能力（NetCapabilities）或 `allowedApplications` 等，试图把容器内应用纳入允许使用该 VPN 的范围。

本质与风险：属应用层务实「**适配**」而非「破解」系统隔离；效果依赖设备 / 系统版本差异，**不稳定**——ClashBox 社区在兼容模式效果不佳时推荐切换 Mihomo 内核，不同内核的网络栈处理（TUN 路由管理、IPv6 支持等）差异提供了另一条路径。

## 3. 对 Arkhon 的初步可行性判定（讨论前先验）

- 三条路径均可**用户态验证**（不依赖 root / 系统权限），符合现有技术边界
- **待验证线索**：设备接口表出现过 `ancormnet0`（`172.17.0.1/24`）——疑似卓易通容器桥接网段；若属实，路径 1（容器网段路由）可作为第一个实验
- 主要风险：平台版本差异导致适配不稳定（需按版本回归）；对现有接管（鸿蒙三方应用）的影响面需评估

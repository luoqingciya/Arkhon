**坑位记录：策略组缓存被带偏（已修，2026-09-28）**

- 现象：隧道已连接，但内核日志全量 `using PROXY[DIRECT]`（出口=直连），浏览器打不开被墙站点（表现为"连着却不走代理"）。
- 根因：mihomo `profile.store-selected` 默认 true —— 上一次会话手选的 DIRECT 经 `cache.db` 被带入新会话（重装 App 不清沙箱数据）。
- 修复：内核配置显式 `"profile":{"store-selected":false,"store-fake-ip":false}`（每次启动按第一个成员选：≥2 节点 = AUTO，单节点 = 该节点）。
- 验证：同日真机复测全量连接命中 `using PROXY[真实节点]`，诊断全过。

**排查记录：网络切换导致隧道悬挂（已修，2026-09-29 · Mate 80 Pro）**

- 现象：隧道在 Wi-Fi 上启动（内核出口绑定 `wlan0`），断开 Wi-Fi 回蜂窝后浏览器全部打不开、App 仍显示「已连接」；自检 `vpn-net / 扩展内核 / 心跳` 全"正常"（都是本地探测），3 分钟后 `隧道出网 code=-1` 但**只记录不重建** → 悬挂无自恢复。反向（蜂窝启动 → 连 Wi-Fi 致蜂窝被系统收起）同样复现。
- 根因：内核启动时把出口绑死 `interface-name`（启动瞬间探测到的物理网卡）；系统切换网络时会收起旧链路（实测：Wi-Fi 连接时蜂窝即从 `getAllNets` 消失），绑定随即失效，全部拨号 `network is unreachable / context deadline exceeded`。
- 修复（两处，2026-09-29）：
  1. `VpnExtAbility`：新增「物理网卡变化检测」——心跳 30s 轮询 + `netAvailable/netLost` 事件去抖 2s，与已绑定网卡不一致即触发扩展内自愈（重探网卡 + 内核重建 + 重新 attach），20s 冷却防抖动；
  2. `TunnelManager`：VPN 网络因重建换 `netId` 后自动 `setAppNet` 重绑（否则主进程自身出网探测 / 订阅刷新会一直失败）。
- 复测：Wi-Fi 断开 → 失败后 **2.1s** 触发重建、**~4s** 全链路恢复（事件路径生效）；主进程重绑 `netId=175` 成功；无重建循环。

**排查记录：浏览器访问 google.com 超时 → 接管范围边界（2026-09-28 深夜 · Mate 80 Pro · 蜂窝）**

- 现象：隧道已连接、App 内「连通性诊断」全过（gstatic=204 / google=200 / example=200），但部分浏览器打不开 google.com。用 chatgpt.com 做了接管范围矩阵复测：

| 浏览器 | 类型 | 结果 | 说明 |
| --- | --- | --- | --- |
| 夸克浏览器 | 三方鸿蒙应用 | ✅ 可用 | 流量被隧道接管，走节点出网（被墙站点 chatgpt.com 全通） |
| 观星浏览器 | 三方鸿蒙应用 | ✅ 可用 | 同上 |
| 华为浏览器 | 系统应用 | ❌ 不可用 | **系统软件不可被三方 VPN 接管**（平台限制） |
| Chrome | 安卓应用（卓易通兼容层运行） | ❌ 不可用 | 兼容层网络栈独立于鸿蒙，流量不走系统 VPN（平台限制） |

- 取证结论（App 侧）：诊断全过、256KB 大文件实测 790ms、`ipv4.google.com`=200；内核 klog 显示失败浏览器时段隧道内**无其任何 google 连接** → 属「流量未被接管」而非「接管后不通」。
- 判定：**Arkhon 自身工作正常**（三方鸿蒙应用含被墙站点全通）；失败两例均为平台接管边界（系统应用 / 安卓兼容层），非缺陷，留档避免重复排查。
- **补充 · 局限性对照（2026-09-29 补记）**：① **鸿蒙原生代理软件（Arkhon）只能代理鸿蒙三方应用**——系统应用、卓易通内安卓应用均不在接管范围；② **卓易通内的安卓代理软件可代理卓易通安卓应用 + 鸿蒙三方应用**（系统应用同样不可）——兼容层路径的接管面反而更大；用户文档 / FAQ 需如实说明该边界与差异。
- 顺带发现：`ipv6.google.com`（App 内探测）超时 → 当时判定「VpnConfig 未启用 IPv6 接管（`isIPv6Accepted` 默认 false）」；登记为 M3 专项（IPv6 接管 / 防泄漏）。→ **M3 已闭环（2026-09-29）**：真实根因是平台对 v6 默认路由写法敏感（「无网关」写法被静默丢弃），改「显式网关」后 v6 进隧道、不再直连泄漏（详见 §3.2）。
- 本轮带进代码的增强：「连通性诊断」扩展为 6 站点 + 256KB 大文件实测（gstatic / google / example / ipv4.google.com / ipv6.google.com / baidu.com）；内核日志流断线自动重连。

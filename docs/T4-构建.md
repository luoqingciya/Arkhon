## 3.1 平板限制详情与适配（2026-09-13）

**现象**：平板安装启动正常、VPN 扩展建链成功（fd=30、内核 attach code=0、节点 delay 693ms、扩展进程 loopback 200 OK），但**主进程流量无法进隧道**（`隧道出网(IP) code=2300007 Failed to connect`、`隧道出网(域名) code=2300006 Failed to resolve`）。

**根因**：平板系统不允许三方应用设置全量默认路由。设备 `/proc/net/route` 只有 `wlan0`/`ancowlan0` 子网路由，**没有 `0.0.0.0/0`**；对比手机可正常写入。系统流量未导向 `multitun-vpn1` 虚拟网卡 → 主进程 TCP 探针在直连路径上失败。

**适配**：`VpnExtAbility.ets` 新增平板分支 `buildTabletConfig()`——路由收缩为受限网段（IPv4 `10.22.0.0/16` + IPv6 `fdfe:dcba:9876::/64`，`isDefaultRoute: false`），保持虚拟网卡/DNS/内核链路不变。设备类型检测 `isTabletDevice()` 暂为占位（默认 phone），待接系统参数判断。

**影响**（2026-09-13 结论）：
- 平板形态 VPN 隧道成立，但仅能接管受限网段内的流量（部分流量仍走直连）；
- 全量接管当时判定需系统级能力（系统应用签名 / root），非三方应用可达成范围 → **PoC 结论登记为「平板支持受限路由」**。

> **更新（2026-09-28）**：平板升级 API 26 后复测，**全量默认路由已放开**（主进程隧道出网 IP/域名均 200，详见 3.2）；受限路由适配 `buildTabletConfig()` 已清理（2026-09-28），「平板支持受限路由」结论随之更新。

## 3.2 平板 API 26 复测：全量默认路由已放开（2026-09-28）

**背景**：3.1 的限制发现于 2026-09-13（平板当时系统低于 API 26）；平板升级 API 26 后按遗留项复测。

**复测方式**：当前 HEAD 构建（`isTabletDevice()` 占位为 false → 平板走 `buildPhoneConfig()` 全量默认路由 `0.0.0.0/0`）→ CLI 打包 + `hdc` 安装 → 应用内点「启动 VPN」。

| 维度 | 结果 | 证据 |
| --- | --- | --- |
| 建链（全量路由配置） | ✅ 系统接受 | `vpn connection created, fd=32 addr=10.21.0.2 route=0.0.0.0/0` |
| 主进程网络绑定 | ✅ | `D5e setAppNet ok netId=109` |
| 主进程隧道出网 | ✅ **200**（对照 09-13 的 2300007/2300006 已解除） | `tunnel-out-ip code=200`（20:50:05、20:54:04 两次）、`tunnel-out-host code=200`（20:50:06、20:54:04） |
| 内核入站实证（流量真进隧道） | ✅ | 内核日志 `[TCP] 10.21.0.2:59880 --> 172.66.147.243:80`（主进程 IP 探针落点）、`10.21.0.2:59192 --> 104.20.23.154:80`（example.com 探针落点）；另有 DNS（8.8.8.8/223.5.5.5:53）与 `49.4.x.x:443/8883` 等其他目标流量进隧道 |
| 网卡与持续自检 | ✅ | `multitun-vpn1` UP（inet 10.21.0.2，RX 154 / TX 112）；tick#2→#9 `vpn-net=109 miss=0`、`ext-kernel OK code=200` |

**口径说明**：`/proc/net/route` 仍不显示全局 `0.0.0.0/0`（三方 VPN 的默认路由不在该 dump 中呈现），09-13 的旧口径不能单独作为「路由失效」判据；复测验收以「主进程隧道出网探针 + 内核入站流量」为准。

**结论**：平板（API 26）全量默认路由接管成立；`buildTabletConfig()` 受限路由分支已清理（2026-09-28）。


## 4.2 日志取证方法（隧道 / 数据面排查，2026-09-28 固化）

> M2 联调「出口走 DIRECT / 浏览器打不开」两次排查沉淀，按需取用。

**① 实时流（盯现场）**

```powershell
$hdc = "d:\Apps\03_Dev_Environment\14_DevEco\DevEco Studio\sdk\default\openharmony\toolchains\hdc.exe"
& $hdc shell "hilog -T TunnelManager,VpnExtAbility,KernelRest,KeepAlive,ProfileStore"
```

- 订阅即回灌缓冲区、之后持续流式输出（主机侧断流需重挂，可包一层循环自愈）；订阅到即 dump 全缓冲的行为也意味着重连会重复旧行，接受即可。
- 判据：内核流量行 `using PROXY[出口名]` → 看走节点还是 DIRECT；**`[klog]` 缺行 = 该流量没进隧道**（配合 App 内诊断区分「未接管」vs「接管后不通」）。

**② 缓冲区快照（复盘最近几分钟）**

```powershell
& $hdc shell "hilog -z 800"                        # 末 N 行（全标签，先到先得）
& $hdc shell "hilog -x" | Select-String "关键字"    # 全量导出（配合主机侧筛选）
```

**③ 设备端持久化（最稳，可跨主机断流）**

- 设备上可能已有全量落盘任务：`hilog -w query` 查看；文件在 `/data/log/hilog/`（`hilog.*.gz`，约 4MB / 2min 轮转，编号循环复用）。
- 冷文件 `hdc file recv` 拉回后解压；**注意**：该格式为二进制日志流（文本嵌在二进制头之间），主机侧需用正则抽取（如锚点 `cn.<bundle>` 后的可读串、`\[\x?klog\] \{"type":"[^"]*","payload":"[^"]*"\}`）。

**④ App 沙箱直读（内核配置 / 调试产物）**

- 路径：`/data/app/el2/100/base/cn.luoqingciya.arkhon/haps/entry/files/`（当前为 777 权限，`hdc file recv` 可直读）。
- 内含 `clash-ext/kernel-config.json`（最终下发配置，用于核对生效项）等；**注意 `clash.log` 实际未生成**（别指望内核文件日志做复盘）。

> 文档版本：v0.3（已按官方文档 + ClashBox 实证二次修订）
> 日期：2026-09-09
> 状态：待立项
> **Phase 0 进展（2026-09-09）**：T1 VPN 能力 ✅（真机建链）· T2 工具链 ✅（Gate-B 真机通过，Go c-shared 可加载）→ **引擎 A（自编内核）障碍解除，路线实质收敛为 A**

## 1. 项目背景与问题

Teyvat Arkhon 桌面端已提供基于 arkhon-core（mihomo fork）的完整代理能力：订阅管理、规则分流、节点测速、TUN/系统代理、系统服务托管。但桌面端的能力被绑定在运行它的设备上，存在三类未满足场景：

| 场景 | 现状痛点 |
| --- | --- |
| 移动办公/通勤 | 手机、平板上没有一体化的分流代理入口，Wi-Fi 与蜂窝网络间无法统一管理 |
| 配置跟随 | 订阅、分流规则、节点收藏等配置被锁在桌面端，跨设备无法同步复用 |
| 接管需求 | 移动端需要统一的全局接管入口（VPN 隧道），局域网/本机直连等粒度由分流规则空置（需对标桌面端行为） |

**本项目的目标**：在 HarmonyOS NEXT 上构建原生的移动端代理客户端「Arkhon」，复用桌面端已验证的协议、分流与测速方法论，承载订阅与规则的"移动延伸"，最终实现**手机 + 平板双形态的统一代理体验**。

---

## 2. 产品定位

- **一句话**：HarmonyOS NEXT 上的开源分流代理客户端，通过 **VPN 隧道**统一接管移动网络流量。
- **核心价值主张**：
  1. **单一接管路径（VPN 为主）**：以 VpnExtensionAbility 建虚拟网卡 + 路由统一接管系统流量。经 ClashBox 实证，**移动端承载代理能力的唯一可靠通路是 VPN**，而非"系统 HTTP 代理 / 应用内透明代理"——后者对三方无开放 API，不纳入主线。
  2. **配置可携带**：订阅链接 URI 导入复用桌面端格式（hysteria2 / vless / vmess / trojan / ss 等），分流预设逻辑与桌面端对齐。
  3. **提瓦特统一体验**：继承桌面端深色玻璃拟态与语义化图标，同一套视觉语言跨端一致。
- **非目标（V1 明确不做）**：不做系统级 TUN 之外的 root 功能、不做多用户计费、不做企业管控。

### 2.1 边界与 No-Go 判据（PoC 前必须冻结）

为避免 Phase 0 结束后被迫推翻定位，先明确"即便 PoC 全部受限"也成立的**最保守可交付下限**，以及触发收缩的信号。

| 级别 | 触发信号 | 收缩后的可交付范围 |
| --- | --- | --- |
| 目标 | —— | **VPN 隧道 + 内置内核（引擎 A）**：订阅/测速/规则/隧道完整 |
| 收缩 | VPN 可用但内核 .so 交叉编译受阻，或工具链成本过高 | **引擎 B1（裁剪 sing-box/mihomo 库）代替自编内核**，能力与目标对齐，工程换实现 |
| **保底（No-Go 判据）** | VPN 不受支持（官方 API 11+ 三方可用，信号为"连 VPN Ext 都无法申请"）或内核编不进去且裁剪库亦不可行 | **纯订阅管理 + 节点测速 + 规则只读工具**（仍可发布，作为独立价值形态保留） |

> 若连"保底形态"都无法成立，则本项目立而不起，应终止立项、回到"仅桌面端 + 遥控"路线。
> 每一项 PoC 结论在评审时都必须落为 **「继续 / 收缩 / 终止」** 三态之一，不能留模糊结论。

> **现状基准（2026-09 二次评审）**：官方 `@ohos.net.vpnExtension`（API 11+）已向三方开放 VPN 虚拟网卡 + 路由管理，权限为公开项（`INTERNET`/`GET_NETWORK_INFO`/`ACCESS_EXTENSIONAL_DEVICE_DRIVER`），无需企业/MDM 权限；ClashBox 已携内置 FLclash 内核上架鸿蒙海外市场。据此，**"VPN 不受支持"与"内核编不进"两条触发信号均已低位化**，No-Go 判据主要退化为工程层面兜底，而非技术不可行。

> **Gate-B 实测（Phase 0，Mate 80 Pro）**：原始 Go c-shared 因 musl `initial-exec TLS` 无法 dlopen，已改用 OpenHarmony SIG 官方 Go fork（`GOOS=openharmony`，内置 general dynamic `TLS_GD`）重编，真机 `T2 loaded=1` 加载成功——**「内核编不进去」的 No-Go 触发信号解除**，收窄到「VPN 不可用 / 真实内核隧道喂流受阻」的工程兜底。

## 3. 目标用户与核心场景

| 用户群 | 核心场景 |
| --- | --- |
| Arkhon 桌面端既有用户 | 通勤路上用手机/平板无缝延续订阅与分流规则；回家切换回桌面端 |
| 鸿蒙设备用户（手机/平板） | 在外网访问、开发调试、视频/社交应用分流加速 |
| 进阶用户 | 自定义订阅、节点测速、规则命中检查，保持与桌面端一致的掌控力 |

**关键用户旅程**：
1. 首次启动 → 引导页选择"导入订阅" → URI/URL 粘贴 → 自动解析为节点列表；
2. 总览页一键启用「全局隧道」→ 状态栏/通知栏展示隧道活动状态；
3. 代理页切换策略组与节点、逐点测速；
4. 规则页查看生效分流规则与命中情况；遇到异常可导出日志反馈。

## 4. 竞品与差异化

### 4.1 同类软件对比

| 维度 | Clash 系 iOS/Android | ClashBox（鸿蒙） | 机场自带 App | 本项目 Arkhon（鸿蒙） |
| --- | --- | --- | --- | --- |
| 平台 | 受限或需 TestFlight/侧载 | 鸿蒙海外市场上架 | 绑定厂商 | HarmonyOS NEXT 原生 |
| 内核 | 各自 | 内置 FLclash（Go→OH .so） | — | **内置 arkhon-core / 裁剪 mihomo** |
| 开源 | 部分 | 开放源码（GPL） | 否 | **GPL-3.0 开源** |
| 配置互通 | 各自壁垒 | Clash 兼容 | 私有 | 与桌面端 Arkhon 订阅/规则格式天然兼容 |
| 分流能力 | 完整 | 完整（Clash 规则） | 简单 | 与内核对齐的规则集/命中统计 |
| 视觉 | 各异 | 提瓦特风 | 广告化 | 提瓦特深色玻璃拟态统一语言 |

**ClashBox 实证结论（对本项目的关键参考）**：
- **内置内核 + VPN 上架已被跑通**——引擎 A（Go→OH .so）技术路线被行业验证，可直接对标而非从头论证。
- **最大实操坑是 VPN 回收**：官方保活方案存在系统级回收，ClashBox 用"内核前台模式 + 模拟后台"规避，且注明属华为系统原因。——本项目的**保活专项必须前置**（见 7.3）。

### 4.2 鸿蒙生态现状与替代行为分析

鸿蒙 NEXT 上成熟的第三方代理客户端被视为"几乎空白"，实则有 ClashBox 一面旗帜（内置内核 + VPN 上架），说明**技术可行、生态在成型**。仍需回答"用户不装、或不用我们时会用什么"：

| 用户替代方式 | 与 Arkhon 的差异 | 风险点 |
| --- | --- | --- |
| 系统自带 VPN/企业隧道 | 系统级、仅直连或企业通道，无多节点/多协议 | 能力有限，但零成本、无隐私顾虑 |
| 自有服务器 + softether/自建 | 通用虚拟通道，无精细分流与订阅管理 | 门槛高，粘性来自"已在用"的存量用户 |
| 桌面端 + 手机远程控制 | 复用桌面端，但移动端无独立代理 | 我们与桌面端一致的配置体系正可覆盖此场景 |
| **已上架的 ClashBox 类客户端** | 已占先发、功能趋同 | 需靠"与桌面端 Arkhon 双端一致 + 提瓦特体验"建立差异，避免同质化 |

**差异化落脚点**：**与桌面端 Arkhon 同一套配置、双端一致**，在 ClashBox 已站稳的 VPN 态上叠加"订阅/规则/测速与桌面端强绑定"的跨端一致性，而非再造孤立客户端。竞品对比结论需在 Phase 0 以真实可安装替代品实测核对为准。

## 7. 技术方案

### 7.1 总体架构

```
┌───────────────────────────── 鸿蒙 Arkhon ─────────────────────────────┐
│  UI 层（ArkTS + ArkUI）                                                 │
│   总览 / 订阅 / 代理 / 规则 / DNS / 设置   （Stage 模型，entry 模块）      │
│        │ 状态@State + @StorageLink（全局 AppStorage）                   │
│  服务与状态层                                                            │
│    SubscriptionManager  ProfileManager  RulesManager  SpeedTester      │
│        │                                                                │
│  接管层：VPN 虚拟网卡 + 路由（@kit.NetworkKit vpnExtension）             │
│        │                        │                                       │
│  内核层（引擎 A / B1）：Go→OH .so，NAPI 绑定                            │
│        隧道/协议/分流/DNS/健康检查        （C 远端面壳仅兜底）            │
│        │                                                                │
│  网络（HTTP/WebSocket/TLS，@kit.SocketKit 供内核上行）                  │
└───────────────────────────────────────────────────────────────────────┘
         │ 订阅数据：本地沙箱（Preferences / 文件）
         │ 证书/日志：本地沙箱，日志支持导出
```

- 状态管理：Stage 模型 + 全局 `AppStorage` + 页面级 `@Provide/@Consume`，不引入第三方状态库（ArkTS 非前端状态库生态）。
- 网络：`@kit.NetworkKit`（连接探测/测速）、`@kit.SocketKit`（底层 TCP/QUIC 差异由引擎层承担）、`@ohos.web`（仅用于需要网页的场景，不承载主 UI）。
- 持久化：订阅档案存沙箱文件（JSON/YAML），设置用 `@kit.ArkData`（DataPreferences）。

### 7.2 内核与接管策略（Phase 0 专题）

**接管方式收敛为「VPN 单路径」**（非双模式）：移动端无三方可用的"系统 HTTP 代理 / 应用内透明接管系统流量"开放 API，唯一可靠通路是 VpnExtensionAbility 建虚拟网卡 + 路由（ClashBox 全走此路径）。详见 5.1。

内核承载在以下两路中二选一，C 仅兜底：

| 方案 | 形态 | 优点 | 风险 |
| --- | --- | --- | --- |
| A. 内核库嵌入 | arkhon-core/mihomo Go 交叉编译 .so + NAPI | 分流/协议能力与桌面端一致，长期最优 | Go c-shared → OpenHarmony 工具链需打通、GPL 合规、体积 |
| B1. 裁剪既有库 | 裁剪 sing-box/mihomo Go 库为 .so + NAPI | 减少自研，复用成熟分流引擎 | 裁剪边界的维护成本、与 arkhon-core 目标保持一致 |
| C. 远端内核 + 面壳 | 鸿蒙端只做 UI，代理服务在桌面/服务器 | 最易落地、复用全部后端 | 离线/断网不可用，违背"原生"初衷，仅作兜底 |

> **取消 B2（纯 ArkTS/C++ 自研分流）**：ClashBox 己用 Go 内核 + VPN 跑通，自研分流（规则匹配、GEOIP/GEOSITE、DNS、连接复用、健康检查）成本失控且无必要。

**决策原则**：Phase 0 以"能力盘点 + 一次真实内核实载"为准。若工具链打通则**优先 A（与桌面端 arkhon-core 同源、能力一致）**；否则降级 **B1（裁剪库）** 作 V1 引擎；C 仅兜底。选型需回填 2.1 的 No-Go 判据 **继续 / 收缩 / 终止** 结论。

### 7.3 移动网络适配

移动网络与桌面差异较大，需在 V1 单独设计并纳入真机验证：

| 关注点 | 处理策略 |
| --- | --- |
| IPv4 / IPv6 | 隧道与解析需兼容双栈；GEOIP/规则命中对 v6 的处理与桌面端对齐 |
| UDP 转发 | VPN 路径下确认内核 UDP（含 QUIC）转发能力与降级策略 |
| Wi-Fi ↔ 蜂窝切换 | 监听网络变化（`@kit.NetworkKit` onNetworkChanged），隧道自动重建，避免会话悬挂 |
| **后台保活（专项）** | 官方 `KEEP_BACKGROUND_RUNNING` + `backgroundModes: dataTransfer` 长时任务为基线；**参照 ClashBox 上内核前台模式 + 模拟后台**，并加入台检测与自恢复（防华为 system 回收）——见下方"保活专项" |
| 电量与流量 | 测速与后台刷新做节流；订阅刷新限制频率并提示流量消耗 |

> **VPN 回收/保活专项**（最高风险项之一，ClashBox 实证务必前置）：
> 1. 基线：官方 `backgroundModes: dataTransfer` 长时任务，隧道运行时驻留通知；
> 2. 增强：对照 ClashBox，提供"内核前台模式 + 模拟后台"开关供重度用户兜底；
> 3. 防御：监听隧道存活，被系统回收后检测并自动重建，提示用户恢复；
> 4. 真机验收：切后台 + 锁屏 30 分钟存活、回收自恢复（见 §5 指标）。

> **DNS 分流联动（VPN 路径下可接管）**：经 VPN 路径（虚拟网卡配置 dns 地址 + 内核自实现解析），nameserver/fallback/policy **可实际生效**，非只读——与引擎 A/B1 的 VPN 接管一致。若落入 C（远端面壳），则退回"只读展示"，作为兜底折损，能力边界随引擎选型明确。

### 7.4 数据与安全

- 订阅内容、节点凭据仅存应用沙箱，不落公共目录；导出日志前做脱敏（掩码密码/指纹串）。
- 与远端的控制链路（若启用引擎 C）使用 TLS + 可选口令鉴权。
- 应用权限按最小化申请：仅在开启隧道时申请网络相关权限，首次触发时明示用途。
- **跨端配置交换=本地文件（已确认）**：支持与桌面端互导配置，仅通过手工导入/导出 `config.yaml`（经安全沙箱 + 文件选择器授权），**不自建云同步**，规避合规与运维成本。

### 7.5 构建与发布

- DevEco Studio（API 26 / `modelVersion 26.0.0`）+ hvigor 命令行构建；AGP 对应 stage。
- 签名：本地调试证书用于真机冒烟；发布走应用市场签名流程。
- 工程：当前 `entry` 单模块起步，能力扩展后再拆 `library`（shared 组件/网络层）模块。
- 现有脚手架说明：bundleName `cn.luoqingciya.arkhon`、`phone+tablet` 已在 `module.json5` 声明，与策划口径一致，无需调整。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **VPN 进程被系统回收**（ClashBox 实证的华为行为） | 切后台/锁屏后隧道中断 | 7.3 保活专项：官方长时任务基线 + 内核前台模式 + 回收自恢复 |
| VPN 权限/API 在某机种受限 | 局部机型无法启用 | Phase 0 复核 API 26 实机；失败则该机型降级 A/B1 无 VPN 兜底（保底形态） |
| Go 内核鸿蒙交叉编译受阻 | 引擎 A 流产 | 降级 B1（裁剪库）作 V1 引擎 |
| 裁剪库（B1）与 arkhon-core 意图漂移 | 能力与桌面端不一致 | PoC 以"能力一致"为验收标准；必要时回归 A |

| 沙盒限制导致部分功能（如临时外部文件导入）受阻 | 交互受限 | 用系统文件选择器 + 授权读权限；在设置页提供"粘贴文本导入"为主路径 |
| 构建/真机验证依赖本机 + 证书，周期长 | 发布节奏慢 | 建立真机冒烟脚本化；CI 预检（见 10 节） |
| GPL 合规错配 | 法律风险 | 保持开源仓库；若嵌内核 .so 则随包附完整源码对应修订版与 LICENSE 说明 |
| UI 双形态适配量大 | 延期 | V1 先做 Phone 优先 + Tablet/折叠屏弹性布局（栅格 2-3 档），不做桌面端 Feature Parity |

## 9. UI/UX 方向

- **语言**：延续桌面端提瓦特深色玻璃拟态（暗色底 + 半透明卡片 + 高光描边），亮色为辅，二者可通过设置即时切换。
- **图标**：语义化、高辨识度（延续桌面端"本地地标式图标"偏好），导航采用图标 + 文字双签名。
- **布局**：Phone 单列/底部主导航；Tablet 使用侧边栏导航 + 内容双栏，复用 `Breakpoint` 断点切换；折叠屏展开态纳入 Tablet 档。
- **动效**：页面切换用轻量位移动画，隧道开关用状态反馈（成功/失败 toast + 状态色），保持与桌面端一致的反馈节奏。
- **后台/通知交互**：隧道运行时提供"运行中"通知（可点击返回总览/显示当前节点/一键断开），离屏/锁屏下状态持续可感知；配合保活常驻。
- **品牌**：统一使用"星芒"图形标识，与桌面端品牌元素呼应；**应用名/图标规避代理高危词**（参考 ClashNEXT 改名 ClashBox），降低应用市场审核风险。

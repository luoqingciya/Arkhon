## 1. 保活基线实现（本轮新增）

| 层 | 文件 | 实现 |
| --- | --- | --- |
| 声明 | `entry/src/main/module.json5` | `ohos.permission.KEEP_BACKGROUND_RUNNING` + EntryAbility `backgroundModes: ["dataTransfer"]` |
| 长时任务 | `entry/src/main/ets/common/KeepAlive.ets` | 申请/停止/定期刷新/盘点长时任务；监听 `continuousTaskCancel` / `continuousTaskSuspend` / `continuousTaskActive` |
| 主进程自检 | `entry/src/main/ets/pages/Index.ets` | VPN 启动即申请长时任务（系统自动挂常驻通知）；每 30s 自检「长时任务 / VPN 网络 / 扩展内核 REST」；每 ~3 分钟隧道出网实测；每 ~4 分钟刷新长时任务；检测到丢失 → stop→start 自动重建（60s 冷却 / 90s 宽限 / 连续 2 次确认） |
| 扩展进程 | `entry/src/main/ets/serviceextability/VpnExtAbility.ets` | 60s 心跳（pid + 本进程内核 REST 自探，断档即冻结/回收证据）；2203002 残留态 destroy→recreate 重拿 fd 重挂内核 |

要点：
- **常驻通知无需自行 publish**：`startBackgroundRunning` 成功即由系统挂通知（无提示音）。
- **接口选择**：`string[]` 重载才返回 `ContinuousTaskNotification`（单枚举重载返回 `void`）；`continuousTaskId` 为可选字段。
- **UID/包名一致性**：`ohpm` 要求依赖名 = 包名（`libentry.so`），否则 IDE 侧 NAPI 类型解析失败。

## 2. 实测矩阵（Mate 80 Pro · API 26 · 蜂窝网络 rmnet0）

### 实验 1：切后台 + 锁屏 32 分钟（无定期刷新）

| 维度 | 结果 | 证据 |
| --- | --- | --- |
| 隧道本体（扩展进程内核） | ✅ **零冻结零重启** | 心跳 `#1 → #38` 严格 60s 一条零断档、`kernel=OK code=200`；扩展 pid 全程未变；CPU 累计 0:02→0:13 |
| 网络面 | ✅ 存活 | TUN 网卡 `multitun-vpn1` 保持 UP（10.21.0.2）；VPN 网络 netId=143 保持 |
| 数据面 | ✅ 存活 | 39 分钟后实测 `tunnel-egress code=200` |
| 主进程（UI/长时任务宿主） | ⚠️ **被系统冻结** | 回前台后首条 tick 为 `#22`（18:17:38），若持续运行应为 `~#77` → 定时器约在息屏 11 分钟后停摆 |
| 长时任务 | ⚠️ **被系统取消** | `tick#22 长时任务: 0 个（已被系统取消）`；解冻后重申请成功（taskId=165） |
| 回收事件送达 | ❌ 未收到 | `continuousTaskCancel` 未在冻结期间派发（回调无法执行） |

关键因果链：`DATA_TRANSFER` 命中「>10 分钟不更新即取消」约束 → 任务被取消 → 主进程失去豁免 → 被冻结；时间点与冻结起点吻合。

### 实验 2：模拟隧道意外丢失 → 检测 + 自动重建（自恢复）

触发方式：临时测试钩子直接停扩展（不复位运行态），模拟「隧道意外丢失」。

```
18:24:45 [测试] simulate tunnel drop: stop ext
18:24:46 tick#2 vpn-net=-1（首次检测）
18:25:16 tick#3 vpn-net=-1 miss=1（宽限期内仅记录）
18:25:46 tick#4 vpn-net=-1 miss=2 → [自恢复] 触发重建：VPN 网络连续丢失
18:25:46 [自恢复] auto-recover: ext stopped, restarting
18:25:46 扩展重启：新 pid → physical-if "rmnet0" → kernel attach fd=32 code=0
18:25:47 setAppNet ok netId=145（重绑新 VPN 网络）
18:26:16 tick#5 vpn-net=145 + ext-kernel OK 200
18:26:46 tick#6 tunnel-egress code=200   ← 重建后出网闭环
```

结论：✅ 检测 → 重建 → 重挂内核 → 重绑网络 → 出网恢复，全链路自动完成（约 60～90s）。

### 实验 3：切后台 + 锁屏 + 每 4 分钟刷新长时任务

验证假设：定期 `updateBackgroundRunning` 能否重置 `DATA_TRANSFER` 的「>10 分钟未更新即取消」计时器。

| 维度 | 结果 | 证据 |
| --- | --- | --- |
| 假设成立？ | ❌ **否** | 任务 18:24:16 启动 → **18:34:19 被取消**（= 启动 + 10.05 分钟），期间 18:28:16 / 18:32:16 各刷新一次 → `updateBackgroundRunning` **不重置**进度计时器 |
| 取消事件送达 | ✅ **能送达**（冻结前） | `18:34:19 [回收信号] 长时任务被取消 id=166 reason=1`（`USER_CANCEL`）|
| 主进程后续 | ⚠️ 再次冻结 | 最后一条 tick `#20 @18:33:46` 后停摆 |
| 扩展进程 | ✅ 不受影响 | 心跳 `#8 → #14` 连续 |

**关键推论**：`reason=USER_CANCEL(1)` 是系统对「DATA_TRANSFER 未更新进度」的强制回收口径（锁屏无人操作）；且**取消事件在进程被冻结前送达** → 可以在取消回调里抢时间做"立即重申请"（实验 4 验证）。

### 实验 4：取消即重申请（抢在冻结前恢复豁免）

机制：监听 `continuousTaskCancel` → **回调内立即重申请**（5s 短冷却），抢在进程被冻结前恢复"长时任务豁免"。

| 周期 | 事件 | 证据 |
| --- | --- | --- |
| 1 | 18:44:58 申请 id=167 → 18:54:58（+10.0min）被系统回收 → 即刻重申请 → id=170 | `[回收信号] 长时任务被取消 id=167 reason=1 **detail=12**`（`SYSTEM_CANCEL_DATA_TRANSFER_NOT_UPDATE`）；`[KEEP] re-arm longtask: 系统回收长时任务` |
| 2 | ~19:04:58 id=170 被回收 → 再次重申请 → **id=171** | `tick#43 @19:05:59 长时任务: 1 个 [id=171 pid=27350 suspend=N]` |

结论：✅ **可循环、可持续**。21.5 分钟内主进程**零冻结、tick 零断档**（tick#1 @18:44:58 → tick#44 @19:06:29 = 43.03 个自检周期，理论 43.0）；扩展进程全程存活。
副产品：取得系统回收的**精确原因码**（`detail=12`），把「`DATA_TRANSFER` >10min 未更新进度即回收」的因果钉死。

### 实验 5：静音音频深度保活（`AUDIO_PLAYBACK` + AVSession）—— ❌ 被系统静音检测反制

机制：静音音频流（48kHz/双声道/全 0，1s 缓冲循环写入，实测精确 1 次/秒无空转）+ AVSession（`activate` + `PLAY` 状态 + 5s 位置心跳）+ 长时任务切到 `audioPlayback`（系统侧确认 `onContinuousTaskStart cn.luoqingciya.arkhon`）。

结果：**无效**。息屏（19:28:10）后约 30 秒主进程被冻结（tick 与写循环双双断档），且**未收到任何长时任务取消事件**（冻结时任务仍为 `id=175 suspend=N` 健康态）。

系统侧证据链（实时 hilog 流，19:28:35 → 19:28:48）：

```
[AudioLogUtils] [IncSilentData][RendererInClient] counts: 3000
[RendererInClientInner] [WriteMuteDataSysEvent] write silent data for some time        ← 检测到持续写静音数据
[TASK_DETECTION] uid:[20020365] all sessions are mute: 1                               ← 判定该 uid 全静音会话
[SUSPEND_MSG] 20020365 enter silent, is all session mute : 1                           ← 进入"静音应用"处理
[SUSPEND_MANAGER] Doze 20020365_cn.luoqingciya.arkhon, C_[2,(0,1,0,0,1,1,1,0,1)], ...
[SUSPEND_MANAGER] Freeze pid: 5165 success.                                            ← 冻结生效
```

结论：**API 26 存在针对"静音音频保活"的专门反制机制**（渲染器静音数据检测 → 静音应用 Doze/冻结），长时任务豁免在此路径下不生效。故"静音音频 24h 保活"在本代系统上不成立——同类应用要么播放**非静音内容**（白噪音/低频音，属主动规避系统策略，上架合规风险高），要么运行在无此检测的旧版本。

回归方法（后续系统版本可复测）：静音流写循环 + 息屏，观察 `WriteMuteDataSysEvent` → `IsAllSessionMute` → `Freeze pid` 三段日志是否仍然出现。

## 3. 关键发现（并入 M3 设计约束）

1. **长时任务保"不被杀"≠ 保"不被冻结"**：`dataTransfer` 任务在系统侧被取消后，主进程随即被冻结（JS 定时器全部停摆），App 侧一切自检/自恢复逻辑同时失效。
2. **内核所在进程天然存活**：VPN 扩展进程由系统托管，32 分钟息屏内零冻结、零重启 —— 隧道数据面可靠性远高于 UI 进程（与 ClashBox 实证一致）。
3. **`continuousTaskCancel` 不能在冻结期送达**：不能作为后台唯一检测手段；检测必须依赖"下一次可执行时刻"的盘点。
4. **`DATA_TRANSFER` 的系统约束是硬约束**：不更新（>10min）/ 低速会取消；`updateBackgroundRunning` **不能**重置该计时器（实验 3 反证），实测有效的对策是「收到取消事件 → 立即重申请」（实验 4）。
5. **`interface-name` 不能写死**：写死 `wlan0` 时，设备切到蜂窝（`wlan0` 无 IP）上游拨号全部超时；已改为运行时探测物理承载网卡（Wi-Fi > 以太 > 蜂窝，跳过 VPN 自身）。
6. **授权回调不可依赖**：系统记住 VPN 授权后不再弹窗，`onAuthorizationResult` 不触发；须以「VPN 网络出现 + setAppNet 成功」作为兜底运行态信号。
7. **系统对"静音音频保活"有专门反制**：渲染器持续写静音数据会被 `WriteMuteDataSysEvent` 捕获 → `IsAllSessionMute` → 静音应用 Doze/冻结（实验 5 实测），该路径不受长时任务豁免保护。因此音频类保活必须播放**非静音内容**才可能生效，属主动规避系统策略（合规风险）。

## 4. 三态结论

| 判据 | 结论 | 依据 |
| --- | --- | --- |
| 隧道端到端 + 锁屏 30 分钟存活 | ✅ **继续** | 实验 1：内核心跳/网卡/出网全存活 32 分钟 |
| 检测 + 自动重建自恢复 | ✅ **继续** | 实验 2：丢失后 60~90s 内全链路自动恢复 |
| 主进程后台保活 | ✅ **继续（A 方案：取消即重申请）** | 实验 4：跨 2 个回收周期零冻结零断档，纯用系统合法信号自我续期 |
| 静音音频强保活 | ❌ **终止（本代系统）** | 实验 5：被系统静音检测反制（`WriteMuteDataSysEvent` → Doze/Freeze），不列入产品方案 |

**对 M3 的输入**：
1. **保活分层**：隧道进程（VPN 扩展）由系统托管，**无需额外保活**；主进程用「取消即重申请」维持后台存活（默认方案），不引入任何伪装行为。
2. **若要更强的主进程保活**：只剩"播放非静音内容"这类主动规避路径，代价是合规风险与用户可感知（媒体卡片），建议不做默认项；如做，须设置项显式开启 + 隐私/用途说明。
3. **自恢复能力增强**：把关键自检与恢复逻辑下沉到扩展进程（对标 ClashBox「内核前台模式」），使主进程被冻结期间隧道仍可自愈。
